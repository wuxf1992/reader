## 优先修复

### 1. 书架刷新仍可能返回内部缓存的旧内容

- **位置与来源**：`web/src/api/client.ts:799`、`web/src/api/query.ts:8`、`web/src/features/shelf/queries/shelf.queries.ts:18`。两套 QueryClient 与两套查询键的结构在主线已经存在；定制仅对最近阅读排序将内部 staleTime 调为 0。
- **具体问题**：书名、作者、入库排序下，外层书架缓存过期或被同步事件失效后，内部导航缓存仍可在 5 分钟内返回旧结果。临时复现：服务端标题改变，时间前进 61 秒并失效外层书架，仍得到旧标题且请求数保持 1；再失效内部缓存才得到新标题，请求数变为 2。
- **最小修复方向**：让 React 页面的刷新同时遵守内部导航缓存的失效规则，先覆盖书架同步完成、显式刷新和写操作；长期以一个查询键/失效入口负责同一资源。保留旧 imperative 调用的缓存和账号切换校验，不能直接删掉整个内部缓存。
- **不处理的影响**：页面看似刷新，跨设备更新的书籍信息仍延迟展示；多个入口继续分别补失效逻辑，后续同步主线更易漏项。

### 2. 书源详情仍有独立的封面加载入口

- **位置与来源**：定制组件 `web/src/features/sources/components/SourceBookDetails.tsx:33`；共享实现为 `web/src/ui/use-cover.ts:6`。
- **具体问题**：详情先清空封面，再等待 `api.coverBytes(...).then(...)`，没有使用缓存回调。相同书籍已有持久封面、网络校验挂起时，共享 hook 已显示图片，详情仍显示“暂无封面”；释放 304 后详情才显示。该情形已用真实 ReaderApi + 本地 transport 复现。
- **最小修复方向**：已入架书籍接回共享封面入口；未入架书源封面保留必要的独立请求取消。统一缓存先显示、304 不重建 URL、拒绝访问后隐藏、账号与服务隔离，保留打开目录时的请求优先级处理。
- **不处理的影响**：同一本书在书架与详情中体验不同；再次修改缓存策略时仍需维护两处图片生命周期逻辑。

## 建议优化

### 3. 繁简选项把整份字典带入首页入口

- **位置与来源**：定制 `web/src/store/settings.ts:4`、`web/src/ui/shelf-settings.tsx:1` 从 `render/chinese.ts` 导入三个选项；同一模块又静态导入 OpenCC 的转换预设。
- **具体问题**：仅显示书架或恢复设置也会加载转换字典，削弱主线阅读页懒加载的收益。临时 Vite 插件仅把这两处选项导入改到轻量虚拟模块，其他运行源码不变，入口由 **1,912,310 B / gzip 718,585 B** 降为 **806,352 B / gzip 240,982 B**；gzip 减少约 **66.5%**。
- **最小修复方向**：把选项和对应类型放到不依赖字典的共享小模块；转换实现继续由阅读页使用。补查繁简转换、搜索、高亮和阅读页离线装载。
- **不处理的影响与实验限制**：每次首屏仍要下载/解析不使用的字典。此次实验把约 1.1 MB 内容移到阅读 chunk，总下载量和 PWA 全量 precache 没有同幅减少；尚未测 iPhone 的启动时延，不把包体积收益写成真机加速倍数。

### 4. 有本机书架时，整个应用启动仍等待登录校验

- **位置与来源**：`web/src/main.tsx:44` 等待 `createAppRuntime()`，`web/src/app/runtime.ts:69` 等待 `/auth/me`；主线也是校验完成后才渲染，定制把无上限等待限制为 3 秒。
- **具体问题**：Wi-Fi 显示联网但服务器无响应时，缓存正文虽已能立即开书，启动阶段仍先停在启动画面约 3 秒。现有 PWA 启动回归证明有时间上限，没有验证“缓存壳先显示、校验后完成”。
- **最小修复方向**：本机账号缓存就绪后先渲染缓存页面，把会话校验放到后台，并以账号/服务代次丢弃迟到响应；明确 401/403 仍退出或清除对应受限展示。不要只去掉 await 而丢失会话事件接线与失败处理。
- **不处理的影响**：弱网和重开 PWA 的首屏仍有固定等待。该项本轮以代码路径审查为依据，未实施新的启动方案。

## 可清理的遗留代码

### 5. 旧设置读写和旧主题应用入口只剩测试调用

- **位置与来源**：`web/src/ui/settings.ts:17` 的 `loadSettings`、`saveSettings`，以及第 46 行的 `applyTheme`。旧读写入口由主线遗留，定制增加了主题兼容逻辑；当前实际偏好存储由 `store/settings.ts` 与共享主题模块负责。
- **具体问题**：全仓库引用检索没有找到这些旧入口的运行调用，只有旧主题测试；它们维护另一个 `reader.settings` 存储键。`applyBrowserTheme` 仍被 ReaderScreen 用于系统栏取色，不能整文件删除。
- **最小修复方向**：删除无运行调用的旧入口及其专属 clamp/isTheme 辅助，迁移有效断言到当前 SettingsStore / 主题入口；保留浏览器取色和真机校准相关测试。预计可减约 50 行运行源码，依赖不变。
- **不处理的影响**：下一次主题更新仍会维护已经不用的旧路径，测试通过也不能证明真实偏好入口正确。

## 后续合并与发布的改进

1. **比较固定版本**：每次 fetch 后固定目标 SHA，同时记录 custom 的起点；用 merge-base 生成上游增量、本地差异和重叠文件清单，优先审阅重叠的阅读/缓存/样式入口。
2. **预演后再建整合 worktree**：先运行 `git merge-tree --write-tree custom <目标SHA>`；0 表示文本合并成功，1 表示有冲突，其他错误单独处理。它不改工作区或索引，但会写 Git 对象。文本合并成功仍要验证行为。[Git merge-tree 文档](https://git-scm.com/docs/git-merge-tree)
3. **补丁与功能分别去重**：`git cherry -v <目标SHA> custom` / patch-id 用于找相同补丁；功能重叠再按上表的等价回归判断，不能根据提交标题或 `+/-` 自动删代码。[Git patch-id 文档](https://git-scm.com/docs/git-patch-id)
4. **继续 merge 和 rerere**：保持 main 纯上游、custom 定制、临时 sync 分支整合；保留现有合并历史。rerere 当前已启用，复用解法后仍审阅 diff 和相关测试。[Git rerere 文档](https://git-scm.com/docs/git-rerere)
5. **缩小后续补丁**：一项功能一个提交；主题数据、书源详情等放独立入口，缓存/分页共享规则在现有核心入口修复。主线已等价覆盖时，提交一笔明确的旧实现删除并记录退场条件。
6. **用同一个已验证点发布**：当前线上前端对应 `28e6d4e`，只回移了缓存与位置修复；custom 还含完整上游整合，两者全树差 119 文件。下一次完整发布应验证实际部署产物与插件兼容，使线上对应 custom 的明确发布标签；紧急回移分支只作为发布记录，不长期另行开发。
7. **完成异机备份**：当前只有 upstream 远端，Reader 的个人 origin 尚未接入。本地 bundle 已验证，但不等于 GitHub 备份。没有新上游提交时无需制造空合并，按优化优先级继续小提交即可。
